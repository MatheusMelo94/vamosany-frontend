### NON-BLOCKING

#### Finding RV-0049: The aside-index click test (AC 23) is flaky under parallel load: the smooth scroll sometimes never moves
- **Location:** `tests/e2e/guias/toc.spec.ts:131-159`; helper `open()` at `:58-62`. Code under test: `features/guias/components/guide-toc.tsx` (the `onClick`, which uses native anchor scroll and does not call `preventDefault`) and `features/guias/hooks/use-align-to-hash.ts`.
- **Convention citation:**
  - per `frontend-architecture-conventions.md § Engineering Workflow` (route-level behavior in Playwright, deterministic).
  - Reviewer Test Quality audit (specs independent and deterministic; no flake retried into green).
  - QA conventions § Accessibility & Performance Gates, as cited by Bug 0016: flakes are fixed or quarantined, not retried.
- **Issue:**
  - At `--workers=2`, the test failed in 2 of 14 loaded runs, and in 0 of 10 runs alone.
  - In both failures the URL hash and the focus were already correct (those assertions passed). The H2's `y` stayed at its unscrolled position (1893) for the full 10 s poll. So the native smooth scroll started by the click was cancelled or never ran.
  - `open()` only waits for hydration, through the first `aria-current`. It does not wait for the motion controller, the webfont reflow or a ScrollTrigger refresh.
  - The likely cause is a layout refresh soon after load cancelling the in-flight smooth scroll. That is the same family as QA bug 0017 (`/#services` direct load ends short with motion) and the one `useAlignToHash` already works around for the hash-on-load case.
  - Not introduced by the fix commits. At 1280, `(min-width: 961px)` matches on mount, so `GuideToc`'s effect runs exactly as before `5c1bfaf`.
  - If the cause is product-side, a real visitor who clicks an index item in the first moments after load would see the hash change and focus move with no scroll. That is why this is not a NIT.
- **Remediation:**
  1. Root-cause it with a trace at `--workers=2 --repeat-each=10`: check whether a `ScrollTrigger.refresh()` or a font-driven reflow lands during the scroll.
  2. If it is test timing only, make `open()` wait for the motion controller and `document.fonts.ready`, as `a11y.spec.ts` now does with `waitForMotionController`, before clicking.
  3. If it is product-side, re-align the target after the click, the way `useAlignToHash` re-aligns on `scrollend` and `load`. That is an Architect call, because it touches the same mechanism as Bug 0017.
- **Routed to:** Frontend Engineer (test, and the trace); QA Engineer informed (`tests/e2e` is QA-owned); Frontend Architect if the cause is product-side (with Bug 0017).

#### Finding RV-0048: RV-0046's px media query can disagree with the rem container query, leaving a visible index without its highlight
- **Location:** `features/guias/components/guide-toc.tsx:18` (`INDEX_VISIBLE = "(min-width: 961px)"`), against `app/globals.css:77` (`--container-guide-aside: 60.0625rem`).
- **Convention citation:** per `frontend-architecture-conventions.md § Accessibility` engineering rules (respect the user's text size). The container width is in rem on purpose (spec § Page Structure G4). Spec AC 22: the active item is marked while reading.
- **Issue:**
  - The index shows when its container is at least 60.0625rem wide. The gate is 961 **px** of viewport. These agree only when the browser default font size is 16 px.
  - **Smaller default font** (for example 13 px, Chrome "Small"): the container breakpoint drops to about 781 px. Between about 781 and 960 px, the aside index is visible, but the scroll work is off, so nothing is marked `aria-current` and the highlight never moves. That is the no-JS state on a JS page.
  - **Larger default font:** the opposite case is waste only. The work runs while the index is hidden, as before the fix.
  - Rare configuration, and it degrades to the documented no-JS behavior, hence NIT.
  - The code comment's reasoning ("container never wider than viewport") holds only at 16 px.
- **Remediation:**
  - Write the query in the same unit as the container: `(min-width: 60.0625rem)`. Media-query rem resolves against the browser's initial font size, which is what the root rem uses here, because `globals.css` sets no root `font-size`.
  - Or gate on the nav's own box (`navRef.current.offsetParent !== null`) re-checked from a `ResizeObserver`, as v1 suggested.
  - Update the comment, and add a unit case that stubs the rem query.
- **Routed to:** Frontend Engineer.
