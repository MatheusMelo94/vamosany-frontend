### BLOCKING

#### Finding RV-0001: New standalone links are below 44 px on coarse pointers (Contacto channels, Colaboraciones partner line)
- **Location:** `features/sobre-mi/components/channel-list.tsx:55-72`; `features/sobre-mi/components/product-ledger.tsx:36-47` (partner `ExternalLink`); `features/sobre-mi/components/external-link.tsx:23-32`
- **Convention citation:** `design-conventions.md § Spacing, Layout & Responsive Breakpoints` ("Touch targets ≥ 44 × 44 px on pointer-coarse devices"); spec v1.1 § Accessibility Acceptance ("Targets: menu items, FAQ summaries, buttons, contact links ≥44×44px on coarse pointers"); plan § 9 (`min-h-11` via `pointer-coarse:`)
- **Issue:** The plan's mechanism was never implemented (`pointer-coarse:` appears nowhere in the repo). Measured at 360 with touch: Contacto email 153×17, Instagram 99×17, TikTok 99×17. Colaboraciones partner-line links are 14 px tall ("Estudio Ulbia ↗" 120×14, "Mona Cases · mayo 2023 ↗" 192×14, "Efe Hus · Flor ↗" 128×14). The contact links are named in the spec's acceptance, and phone use is the user's hard requirement. FAQ summaries (`min-h-11`), buttons (`min-h-12`) and form controls pass. Links inside running prose are exempt (WCAG 2.5.8 inline exception) and are not part of this finding.
- **Remediation:** On the channel links and the partner-line links, add `pointer-coarse:inline-flex pointer-coarse:min-h-11 pointer-coarse:items-center` (on the `<a>`, or via a `className`/`size` prop on `ExternalLink`, so the inline story links stay untouched). Check that the 200px notes column and the "break only after @" rule still hold at 1280, since `pointer-coarse` doesn't apply there. Add an e2e test at `phone-360` (hasTouch) asserting a bounding box ≥ 44 px for `[data-sm-channels] a` and `[data-sm-partner] a`.
- **Routed to:** Frontend Engineer

### NON-BLOCKING

#### Finding RV-0003: `opacity` instead of `autoAlpha` has no recorded decision
- **Location:** `features/sobre-mi/motion/scenes/reveals.ts:9-22` (rationale), plus `entrance.ts`, `sobre-mi.ts`, `colaboraciones.ts`, `trabaja-conmigo.ts`, `contacto.ts`, `faq.ts`, `form-feedback.ts`
- **Convention citation:** `frontend-architecture-conventions.md § Animation (GSAP 3)` ("Animate transform and opacity (use autoAlpha)"); spec § Motion Intent M1–M7 (written as `autoAlpha`)
- **Issue:** The Engineer's reasoning holds, and it matches the frozen landing: with autoAlpha, unrevealed fields and links leave the tab order and the a11y tree, and the "20" `sr-only` twin flaked out of the tree. But the rule is broken across the whole feature, and the only record is the commit bodies.
- **Remediation:** Record the decision as an ADR ("reveals of content that is or contains focusable elements use opacity, not autoAlpha; initial state stays `opacity: 0` under `.gsap`"), or amend § Animation (drift below). No code change.
- **Routed to:** Frontend Architect (UX Strategist informed: the spec text says autoAlpha)

#### Finding RV-0004: The First Load JS self-test is red at HEAD
- **Location:** `scripts/check-first-load.selftest.mjs:62,93` (`/\+0 B of the/` on the clean and reverted builds); `perf/first-load.json`
- **Convention citation:** `frontend-architecture-conventions.md § Performance Budgets`; tasks T043 ("A self-test proves … passes on the clean build")
- **Issue:** The self-test assumes a clean build equals the baseline. Since `595b968` the baseline is the pre-M4 value, so a clean build reports +206 B (Engineer's environment) or −109 B (mine). Result here: FAIL clean, FAIL +1, PASS +2,000, FAIL reverted. The guard still detects growth correctly (+1 B was reported as a 1 B delta), but its proof is broken. The spread between environments also means the effective headroom on `/` (at 98.9% of budget) depends on where the check runs.
- **Remediation:** Measure the clean build first, then assert the +1 and reverted cases *relative to that measurement* (Δ = +1 B, Δ = 0 B) and the +2,000 case against the allowance. Record in `perf/first-load.json` (or the plan) which environment the baseline was measured in, and have CI use the same install layout.
- **Routed to:** Frontend Engineer

#### Finding RV-0005: A desktop mega-menu stays open after keyboard focus leaves it
- **Location:** `components/layout/navbar.tsx:134-209` (panel open state is cleared only by Esc, a click, or mouseleave)
- **Convention citation:** `design-conventions.md § Accessibility Baseline` (full keyboard path; focus visible); spec § Accessibility Acceptance (keyboard path, menu; "Focus not obscured (2.4.11)")
- **Issue:** Probe at 1280: Enter on "Sobre mí", then Tab through the 5 items, the language button, Log in, Sign up and into `<main>`. The panel stays open over the page the whole time. T009 made the panel items part of the tab order, which widens this older behavior. The open panel covers the top ~320 px of the viewport, so focused page content that is already on screen can end up under it.
- **Remediation:** Close the panel on `focusout` of the trigger's `<li>` when `relatedTarget` is outside it (keep Esc → trigger focus). Add an e2e step: Tab past the last item → `aria-expanded="false"`. No pixel change in the closed or hover states.
- **Routed to:** Frontend Engineer

#### Finding RV-0006: Drawer menu items are 22 px tall on phone; the spec's target rule conflicts with the frozen drawer

- **Issue:** The five "Sobre mí" drawer items measure 286×22 at 360. They pass WCAG 2.5.8 through spacing, but not the spec's own 44 px acceptance. Fixing this changes drawer pixels, which ADR-0006 freezes, so this is a spec conflict and not purely an Engineer defect.

#### Finding RV-0007: Timing-sensitive e2e: 6 failures under parallel load, 31 hard-coded waits
- **Location:** `tests/e2e/sobre-mi/motion.spec.ts:186, 724` (and 16 more `waitForTimeout`), `tests/e2e/sobre-mi/structure.spec.ts:93, 105` (30 s test timeouts), `tests/e2e/navbar.spec.ts:261-262, 304` (3 s dot poll), `tests/e2e/sobre-mi/forms.spec.ts` (10 waits), `faq.spec.ts:144, 235`
- **Convention citation:** `frontend-qa-conventions.md § Accessibility & Performance Gates` (flaky tests quarantined, never retried into green silently); Reviewer Test Quality ("no hard-coded waits")
- **Issue:** Running with `--workers=2` next to QA's 4-worker run produced 6 failures: the heading stayed at opacity 0 within 5 s, a year-tick sample was missed, metadata/landmark tests timed out at 30 s, and the dot didn't settle within 3 s. All pass 3 out of 3 times serially. CI has `retries: 1`, which would hide exactly this kind of failure. Frame sampling for motion is legitimate. Fixed "settle" sleeps (`motion.spec.ts:93` 2,500 ms, `navbar.spec.ts:76` 1,500 ms, `forms.spec.ts:318` 1,000 ms) and short polls are the fragile parts.
- **Remediation:** Replace settle sleeps with `expect.poll` on the actual condition (the controller has mounted, e.g. `ScrollTrigger.getAll().length`, or `waitForMotionToSettle`). Give motion assertions a generous `timeout` rather than fixed sleeps. Run the Sobre mí set in CI at `--workers=2` once to confirm. Quarantine any remaining flake with `test.fixme` + bug ID.
- **Routed to:** Frontend Engineer (spec files) + Frontend QA Engineer (shared journey files)

## Audit notes

There is no `'use client'` on layouts or pages, and client leaves stay minimal (forms, `FaqDeepLink`, `CuadernoMotion` → dynamic controller, `NavMarker` dynamic). T013's verbatim oracle and T044's R-01 no-leak tests are exemplary. No Draft or Pre-Contract labels are open. Pre-Convention: none (RV-0003 should have carried one).
